Bulk import

Import a dependency-inventory JSON

Branches in the file are added or updated; nothing else changes. If any entry is invalid, nothing is imported.

Format help

Dependency-inventory JSON (a .json file, nothing is fetched): a root array with one object per code repo branch: required name, url and branch (no default branch is assumed); optional appId, provider (one of github), sbom (url may be null, generatedAt), projects (path, ecosystem, packageManager, resolution); and a required dependencies array ([] for none) with one row per resolved graph edge: name, version, optional purl (its version must equal version), scope, dependencyType, depth, parentCoordinate, projectPath and more. Every row is kept with its snapshot; each distinct package + version is listed once for EoL matching. Listed branches are added or updated; branches not in the file are left untouched (nothing is deleted). Every entry is checked before anything is saved; if one fails, the whole file is rejected. A branch gets a new snapshot when anything except sbom.generatedAt changed. URLs and evidence paths in the file are recorded as provenance and never fetched; re-upload the JSON to update a branch.

The demo JSON holds eleven fictional DEMO code repos (example.invalid placeholders, not remotely hosted), each on main and release/legacy, resolved with Maven, Gradle, NuGet, pip, pip3, uv, npm and Yarn; every row comes from a native dependency-tree run. Each branch includes a lifecycle-tracked dependency, which the catalogue links to release cycles. Upload it here to try the app; EoL dates still come only from the real endoflife.date catalogue.

Import an SBOM for one code repo branch

Only the file is required; nothing is guessed from it or its name. Without both URL and branch, the same file with the same details updates the same entry. The branch's inventory becomes exactly the packages in the file. If the file or any package is invalid, nothing is imported.

SBOM help

Supported (detected from the content, not the file name; nothing referenced in the file is fetched): CycloneDX 1.4, 1.5 and 1.6 as JSON or XML (every component, nested or unreachable, except the metadata.component root and file/data components); SPDX 2.2 and 2.3 as JSON or tag-value (every package, including the described root; files are not packages); and an ISO/IEC 19770-2:2015 SWID tag holding exactly one SoftwareIdentity (its software, not its payload files). Every package needs a name and version. A purl without a version gets the package version. An empty components/packages array deliberately empties the branch; a missing one is rejected. Not supported: SPDX 3, SPDX RDF/XML/YAML, CycloneDX before 1.4, XML with a DOCTYPE.
